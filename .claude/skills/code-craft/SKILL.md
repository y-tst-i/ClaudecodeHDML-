# code-craft：コードで作る、撮って見る、直す

AIに一発で作らせると、誰が頼んでも似た「それっぽい平均」になる（黒背景・太字・パーティクル・グリッチ、グラデの丸、同じ大きさのカード3枚…）。
品質を上げるのはプロンプトの長さではなく、**具体的な画を見ながら何周も直すこと**と、**センスを言葉にして守らせること**。このスキルはその仕組み。

すべての成果物をコードで作るのは、1か所ずつ直せて、同じコードから映像・Web・スライドを出せて、何度でも同じ画を撮れるから。

## 0. 媒体を決めて手引きを読む

| 媒体 | 手引き | 撮り方 |
|---|---|---|
| 映像（モーショングラフィックス、ショーリール） | `references/motion.md` | 時刻で撮る（`--mode time`） |
| サイト（LP、ポートフォリオ、体験型） | `references/site.md` | 画面サイズで撮る（`--mode page`） |
| スライド | `references/slides.md` + `assets/slides-template.html` | 1枚ずつ撮る（`--mode slides --pdf`） |
| 複合（同じ世界観で映像＋サイト＋スライド） | 該当する全部 | 世界観のトークン（色・書体・動きの速さ）を1ファイルに集約して共有する |

どの媒体でも `references/sense.md`（センスとAIっぽさの回避）を読む。

## 1. ブリーフ：白紙から始めない

ユーザーに完成像まで考えさせると手が止まる。必要なのは次だけで、足りなければ1回でまとめて聞く（揃っていれば聞かずに進む）。

- 何のために、誰が見るか
- **印象**（形容詞2〜3個。例：疾走感・ユーモア・硬質）
- 使える素材（ロゴ、写真、3Dモデル、既存サイト、ブランドカラー）
- 制約（尺、枚数、締切、画面サイズ）
- ユーザーのセンスのルール（あれば。プロジェクトの CLAUDE.md も見る）

アイデアが雑なメモでも構わない。「アイデアはヒント、再現を目指さなくていい、表現は過剰でもOK」という前提で、**構成案はAIが先に出す**。人間は判断とFBに集中する。

## 2. 構成表をデータで作る

1行1単位の表を、プロジェクト内のデータファイル（`cuts.js` / `sections.json` / スライドHTML自体）として作る。チャットに書くだけにしない。表は撮影結果と並べてFB表になる。

| 媒体 | 1行の単位 | 列 |
|---|---|---|
| 映像 | カット | ID・尺・はじめ/おわり・動き・Webでの操作・FB |
| サイト | セクション | ID・見せたいこと・肝（一番目立たせる1点）・操作・FB |
| スライド | 1枚 | ID・言いたいこと1文・肝・FB |

**各行に「肝」を1つ決める**のが重要。全部を同じ熱量で作ると視線が迷い、AIっぽくなる。

## 3. 技術検証を先にやる

表現のうちリスクが高いもの（シェーダー、3Dモデル、深度推定、物理、大量の要素、重い演出）は、本番の前に小さく試作して撮る。結果を見せて「これなら企画をこう変えられる」と提案してよい（検証の結果、パーティクル案を捨てて「素材の図鑑」に変えたら良くなった、という例がある）。できないことを本番の途中で知るのが一番高くつく。

## 4. v1 を作る

- 時間・乱数・状態を決定論的にする（同じ入力なら同じ画）。撮影・比較・映像書き出しの前提になる。
- 色・書体・余白・動きの速さはトークン（CSS変数や config）に集約する。
- 未完成に見えるもの（仮テキスト、素のデバッグ表示、Normal/Depthなどの素の質感）は見せる前に消す。

## 5. 撮る → 自分で見る（ここを飛ばさない）

```bash
node .claude/skills/code-craft/scripts/shoot.mjs <URL|HTML|dir> --out out/shots/v1 [--mode time --times 0,2.5,5 | --mode slides --pdf | --viewports desktop,mobile --full]
```

- `sheet.png` を **Read で実際に見る**。コードを読んだだけで「できました」と言わない。コードからは分からない問題が画にはある：文字がオブジェクトの裏に隠れる、ラベルが画面の端で切れる、CSSで `hidden` が効かない、ハイライトが白く飛ぶ、横にはみ出す。
- `review.md` の「⚠ 検出されたエラー」（JSエラー、横はみ出し）は必ず潰す。
- `references/sense.md` のチェックリストで自己レビューし、`review.md` の「自己レビュー」列に書く。**最低1周は自分で直してから**ユーザーに見せる。
- 操作がある成果物（体験型サイト、スライド送り）は、Playwrightで実際に操作して最後まで進めるか確かめる。操作同士がぶつかるバグ（ドラッグを離した瞬間のクリック等）は操作しないと見つからない。

## 6. FB表で回す

- ユーザーには `sheet.png` と `review.md` を渡し、「FB列に書いてもらえれば、全部反映して撮り直します」と伝える。
- FBは1件ずつ対応し、「対応」列に何をしたかを書く。撮り直しは `out/shots/v2` のようにバージョンごとに分け、前の版と並べて見られるようにする。
- 曖昧なFB（「なんかチープ」）は、画を見て原因の仮説を2〜3個立て、直した案を並べて選んでもらう（例：E1・E2・E3）。言葉で聞き返すより早い。
- 「本気でやって」と言われたら、質感・モーション・テンポ・タイポの全部の密度を上げる合図。直す箇所を増やすことで応える。

## 7. CGっぽさ・AIっぽさを消す

コードだけの画は綺麗すぎる。必要なところに、実在の質感を足すことを提案する：

- 実写テクスチャ（ガラスのヒビ、網点、レンズの汚れ、紙、ノイズ）：用途・推奨解像度・探し方を表にしてユーザーに集めてもらう。置き場所は `public/textures/`。
- 画像生成：看板・小物・背景は1枚ずつ作るのを提案。必要な画像のリスト（サイズ・内容・プロンプト・材質の指定）を表で出す。
- UIは逆に引く。シーンが派手なほどUIは静かに（`references/sense.md`）。

## 8. センスを蓄積する（ノウハウを集めるだけで終わらせない）

FBのうち他の場面にも効くもの（例：「ホバーで浮かせない、色の変化だけ」「1枚に肝は1つ」）は、**ユーザーに確認したうえで**プロジェクトの `CLAUDE.md` の「センス」節に1行で追記する。次回以降はそのルールで自己レビューされるので、同じFBを二度言わせずに済む。これがこのスキルの複利になる。

## 終わり方

完了報告には、最終の `sheet.png`、`review.md`、各版で何が変わったかの短い一覧を付ける。映像なら mp4、スライドなら PDF も付ける。
